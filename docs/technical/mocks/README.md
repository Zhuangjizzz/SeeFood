# 接口模拟样例与验证

本目录是 v0.1 开发文档的附件，用于实现固定模拟服务和联调用例。AI 回复均为虚构样例，不是正式 Prompt 或真实模型效果。

- [OpenAPI 定义](../openapi.json)：请求、响应、状态与字段的唯一结构定义。
- [fixtures.json](fixtures.json)：35 组请求／响应交换样例，另含 12 组应被结构校验拒绝的输入或结果。
- [scenarios.json](scenarios.json)：23 个场景，关联[功能规格 D01–D20](../../product/functional-spec.md#9-本轮开发验收用例)及各自需要的交换样例。
- [技术设计](../design.md)：版本、任务、保存、过期、删除和跨对象约束的语义依据。

## 使用方式

1. 先选择场景，按 `setup` 准备本机与服务端状态；`fixtureIds` 对应交换样例的 `id`。这些样例不是一份按文件顺序执行的会话。
2. 除登录外，由本地模拟运行器注入相应测试所有者的业务令牌。模拟场景选择留在开发配置中，不增加生产接口里的任意状态注入参数。
3. 为每张图片分别跟踪上传、卡片和译图任务；按场景触发状态变化。首次上传的 S06 先建待上传快照，再将上传确认后的 assetId 写入新版本，最后按新版本创建任务。退出或网络断开后，已接收任务仍应在真实的本地持久化任务系统中继续。
4. 幂等重放必须复用原键和业务 ID。新记录、过期后重建的上下文、新草稿翻译须按场景生成新 ID，并一致替换相关引用。场景中的旧版本、旧尝试和跨所有者输入用于验证拒绝行为。
5. 本机保存失败、离线、删除标记、页面切换属于客户端或运行环境事件，不能伪造成后端 HTTP 成功响应。需要使用可控制的本机存储、网络和时钟来触发。
6. 样例只有图片元数据，`example.invalid` 地址不提供文件。界面实现阶段需准备实际单图、多图和长图文件，再验证全屏缩放与离线副本。样例到期时间只演示格式，不是保留时长的承诺。

本轮正式接口与模拟接口共用数据结构；本地测试身份使用独立 `/v1/dev/session`，正式环境关闭该路由。领取上传凭证后，按 `uploadMethod`、`uploadHeaders` 请求动态上传地址，不附加业务 Bearer 令牌。

## 场景覆盖

| 场景 | 检查重点 |
| --- | --- |
| S01–S05 | 主入口、输入模式、多图、新建与追加、长图筛选、无卡片、无需译图、局部失败 |
| S06–S08 | 手动恢复待上传材料、退出／重启恢复、部分回复、重试与迟到旧尝试 |
| S09–S13 | 离线副本、空间不足与保存回执、独立收藏、删除竞态、偏好版本 |
| S14–S18 | 五语言布局、已移除功能边界、过期恢复、无菜单沟通、编辑草稿后的旧翻译 |
| S19–S23 | 冻结快照、当前问题不重复、所有者隔离、幂等冲突、跨对象校验与短期地址续取 |

`scenarios.json` 中的 `specified_not_executed` 保留场景定义发布时的状态；它不是当前运行结果。实际实现、相关测试与原生页面证据统一见[核心实现验证](../validation/2026-10-06-core.md)，不把场景定义本身计为已经通过的用例。

## 聊天半段失败联调

使用 `SEEFOOD_MOCK_SCENARIO=chat-partial-failure SEEFOOD_CHAT_PARTIAL_DELAY_MS=6000 npm run server:dev`，导入菜单并进入对话。每个新聊天任务的第一次尝试先发布 `complete=false` 的固定片段，等待后失败；点击该回复的重试操作，第二次尝试生成完整回答并替换同一回复。新建另一问题可以重复此场景。图片处理仍使用正常样例。

片段和任务状态写入实际 SQLite，使用相同 `SEEFOOD_DATA_DIR` 重启服务可以恢复。重试的 `queued.output` 按契约为 `null`，客户端在原消息中保留已保存的片段；进入新尝试后发布的正文整体替换旧正文，不拼接两次尝试。重开只查询原任务，未能确认接收的请求由用户显式继续，复用已保存的正文和幂等键。

`tests/chat-retry.test.js` 在公开 HTTP、客户端业务与 Page 边界覆盖该流程及故障；实际模拟器的可见状态、触控与键盘另行检查。

## 文档静态校验

已使用 OpenAPI 规范校验器及 JSON Schema 2020-12 校验器检查接口定义与交换样例：

- 11 个路径、12 个操作的 OpenAPI 3.1.1 定义通过结构校验。
- 54 个正常请求／响应正文通过对应结构校验；包括用于模拟业务失败的合法错误响应。
- 12 个无效例被拒绝，覆盖独立沟通误带 recordId、菜名纠正字段、非法尝试／版本、成功却不完整、任务／结果类型错配、未支持语言和浮点金额等。

这些静态结果只证明文档结构及样例符合契约。D01–D20、服务重启、竞态和代表性微信开发者工具检查的运行结果见[核心实现验证](../validation/2026-10-06-core.md)；真实登录和 AI 效果留待实际接入后验证。

## 饮食偏好检查运行场景

本地服务执行真实持久 `dietary_review` 任务。默认固定生成对有偏好的样例返回 `possible_conflict`；缺少依据时返回 `unknown`。它不把“示例炒饭”中可能存在的食材当成已确认配料。`SEEFOOD_MOCK_SCENARIO=dietary-conflict` 明确模拟含蛋样例，遇到蛋过敏或纯素限制时返回 `conflict`；`dietary-failure` 模拟检查失败。以上是生成边界上的固定情景，不是实际餐厅或食物判断。

成功提示逐项绑定菜品 ID 和偏好版本。`concern` 是可选契约字段，旧样例缺失时仍合法且按未知处理；`warnings` 保留该菜品的生成语言。确认清真或犹太洁食要求时，固定提示保留认证、配料与制作条件待核实说明。

推荐快捷问题使用相同的固定分类。保存蛋过敏或纯素偏好后，`dietary-conflict` 场景中的明确含蛋例不进入建议；默认场景仍保留可能冲突与待核实原因，不从可能配料推断明确安全。详情可以直接提交 `chat-dish-accepted` 示例中的具体菜品问题，不必等待重查任务。实际输入、任务接收、保存和重开见 `tests/chat-dietary.test.js`；原生模拟器核验另行记录。

## 临时材料到期与续取

S16／S23 的本地运行使用 `SEEFOOD_CONTEXT_RETENTION_MS` 与 `SEEFOOD_ARTIFACT_URL_TTL_MS` 分别控制新上下文硬期限和下载凭证期限；既有上下文不因配置变化延长或缩短。可选 `SEEFOOD_SAVED_CONTEXT_RETENTION_MS` 只在完整保存回执且无活动／待提交依赖时提前清理。

`tests/retention-http.test.js` 在真实 HTTP、SQLite 和图片文件上用可控时钟验证硬到期、下载续取、回执／依赖保留，并通过 SIGKILL 后同目录重启验证过期工作不会恢复写回。`tests/context-rebuild-client.test.js` 通过实际本机文件与 HTTP 验证离线历史、主动聊天／追加／重试重建、消息身份、缺图、丢响应和保存失败。原生模拟器及真机检查分别记录，不能由这些测试代替。
